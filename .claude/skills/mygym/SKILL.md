# MyGym — Contexto del proyecto

Skill viva: se va completando a medida que trabajamos en el proyecto. No repetir acá lo que ya es obvio leyendo el código — solo lo que no es evidente a simple vista.

## Stack (verificado 2026-09-03)

- Frontend: Angular 22.1 (standalone components), generado con Angular CLI 22.1.7
- Ionic 9 + Capacitor 8 — app híbrida (web + móvil nativo)
- Testing: Vitest (`ng test`), jsdom como entorno DOM
- Estilos: SCSS
- HTTP: `HttpClient` de Angular. `HealthService` pega a `${environment.apiUrl}/actuator/health` — el backend expone Spring Boot Actuator, por lo tanto es un backend Java/Spring
- Package manager: npm 11.16.0
- Estructura hasta ahora: `src/app/core/services/` para servicios transversales, `src/app/pages/` para páginas (empezó con `home`)

## Decisiones y convenciones

- (2026-09-03) Multi-tenancy: shared schema + columna `gym_id` en cada tabla tenant-scoped (no schema-per-tenant ni DB-per-tenant). En el backend, `gym_id` es un `Long` plano (no `@ManyToOne`) — patrón a replicar en todo dominio futuro (usuarios, matrículas, pagos).
- (2026-09-03) ~~DB: H2 en memoria~~ **Reemplazado el mismo día por Postgres real en Supabase**, en todos los entornos (no hay perfil H2 de respaldo). Credenciales vía variables de entorno `SUPABASE_DB_URL` (formato JDBC: `jdbc:postgresql://<host>:5432/<db>`, sin usuario/password embebidos), `SUPABASE_DB_USER`, `SUPABASE_DB_PASSWORD` — nunca hardcodeadas en `application.yml` ni commiteadas. `ddl-auto: validate` — Flyway sigue siendo la única fuente de verdad del schema; las migraciones ya estaban en SQL portable, corrieron sin cambios contra Postgres real.
  **Consecuencia importante:** los tests backend (`GymControllerTest` con `@SpringBootTest`, sin `@Transactional`) ahora corren contra la Supabase real, no contra una DB descartable — pueden dejar filas residuales. `GymRepositoryTest` (`@DataJpaTest`) sí hace rollback automático. Si se corren tests seguido, evaluar agregar `@Transactional` a `GymControllerTest` o volver a un perfil de test aislado.
  **Para correr el backend localmente ahora es obligatorio tener seteadas esas 3 variables de entorno** — sin ellas el arranque falla al no poder resolver el datasource.
- (2026-09-03) Backend: paquetes planos por capa (`models`, `services`, `repositories`, `controllers`) + subpaquetes `models.dto` (records) y `services.exception`. Sin auth/Security todavía — módulo futuro separado.
- (2026-09-03) Frontend: páginas nuevas anidadas bajo `src/app/pages/<dominio>/` (ej. `pages/admin/gyms/`), no se introdujo `features/`. Un solo componente sirve para crear y editar cuando el flujo lo permite (ruta con `id` opcional).
- (2026-09-03) Landing pública de marketing en la ruta raíz (`pages/landing/`), montada donde antes vivía el scaffold de health-check (movido a `/status`). Tokens de marca (paleta, fuentes) como CSS custom properties globales en `styles.scss`, mapeados también a las variables de Ionic (`--ion-color-primary`, etc.) para que toda la app herede la identidad. Fuentes self-hosted vía npm (`@fontsource/*`), no Google Fonts por link tag.
- (2026-09-04) **Paleta de marca: "Teal Charcoal + Electric Cyan"** ~~acento cián `#06aebd`~~ **vuelta a lima el mismo día a pedido del usuario** ("volvamos al color lima... manteniendo el color del fondo") → paleta final **"Teal Charcoal + Kinetic Lime"**: fondo `#1e2c30` (carbón con tinte teal, sin cambios), acento único `--brand-accent: #c6ff3d` (lima), `--brand-accent-contrast: #1a2b00`, texto `#eaf6f7`/`#a9c2c6`. El fondo carbón medio se mantuvo porque el claro hacía que las fotos oscuras del gimnasio se vieran "pegadas" en vez de integradas. Tipografía: **Barlow Condensed** (headings) + **Barlow** (body/UI) — sugerencia de `ui-ux-pro-max` por asociación sport/fitness/atlético; Space Mono para cifras (precio, hora, cupos). Cualquier color/gradiente hardcodeado en rgba (no usando los tokens `--brand-*`) queda desincronizado si se vuelve a tocar la paleta — vigilar que no se agreguen nuevos.

- (2026-09-04) **Textura de fondo (grano sutil) en toda la landing** vía SVG `feTurbulence`+`feColorMatrix` (blanco, alfa máx ~0.05) como data-URI, inyectada en el `--background` de `.landing-content` (`ion-content`) combinada con el color: `--background: url("data:image/svg+xml;base64,...") repeat, var(--brand-ink);`. **Gotcha de Ionic:** `ion-content` NO pinta `--background` en `.inner-scroll` ni en el host — lo aplica en un div interno del shadow DOM `#background-content` (`part="background"`). Cualquier intento de texturizar el fondo con un `::before`/regla CSS directa sobre `.landing-content` o `.inner-scroll` no se ve; hay que pasar el valor completo (imagen + color) a través de la custom property `--background`, que Ionic sí reenvía a ese div interno. Verificar con `getComputedStyle(ionContentEl.shadowRoot.querySelector('#background-content'))`.

Es un segundo `project` en `angular.json` (`main.landing.ts` bootstrapea el componente `Landing` directo, sin `app.routes.ts` ni Router) → `dist/landing/browser`, sin ningún chunk de admin. `Landing` no depende de Router (nav interna es por anchors `#hash`), por eso esto funciona sin duplicar código. Verificado sirviendo el build está con `http-server`: `/admin/gyms` y `/status` dan 404 (no existen en este bundle).

Es el comportamiento esperado, no un bug; para probar el envío real hay que estar en el deploy de Vercel con `RESEND_API_KEY` configurada.

- (2026-09-07) **`mygym-api` desplegado en producción: Railway.** Proyecto `mygym-api`, servicio `api`, build automático con Railpack (detecta Maven solo). Dominio: `https://api-production-be95.up.railway.app`. Env vars cargadas ahí: las 3 de Supabase + `APP_JWT_SECRET` + `GOOGLE_CLIENT_ID` (ya con el Client ID real de Google Cloud, proyecto `apruebapyme`). `server.port` pasó a `${PORT:8080}` (Railway inyecta `PORT`, local sigue en 8080 por default). `environment.ts`/`environment.development.ts` del frontend ya apuntan a esta URL y tienen el Client ID real. `mygym.cl` en producción ya funciona de punta a punta (login Google real, `/admin/gyms` y `/gym-admin` con datos reales).
  **Gotcha importante — Supabase direct connection es IPv6-only, Railway no tiene salida IPv6:** el host directo `db.<ref>.supabase.co` da `SocketException: Network is unreachable` desde Railway. Fix: usar el **Session pooler** de Supabase en vez de la conexión directa (Supabase dashboard → Connect → tab "Direct Connection string" → radio "Session pooler", ahí muestra host/puerto/usuario correctos). Cambia tanto el host (`aws-0-<región>.pooler.supabase.com:6543`, no `db.<ref>.supabase.co:5432`) como el usuario (`postgres.<project-ref>`, no `postgres` a secas) — la contraseña es la misma.
  **Segundo gotcha, más grave — el pooler rompe los prepared statements de JDBC.** Con el connection string de arriba, cualquier request a un endpoint que hace SELECT-por-id (`GET /api/gyms/{id}`, etc.) fallaba con 500 en producción: `PSQLException: bind message supplies 1 parameters, but prepared statement "S_8" requires 0`. Causa: el pooler de Supabase (aunque la UI lo llama "Session pooler") enruta las conexiones de forma que el nombre de prepared statement cacheado por el driver de Postgres para una conexión previa choca contra otra distinta del pool — el problema clásico de PgBouncer/Supavisor en modo transacción con drivers JDBC que cachean statements preparados del lado del servidor. **Fix:** agregar `?prepareThreshold=0` al final de `SUPABASE_DB_URL` (`jdbc:postgresql://aws-0-<región>.pooler.supabase.com:6543/postgres?prepareThreshold=0`) — esto le dice al driver que nunca use prepared statements del lado del servidor. Sin este parámetro, cualquier hosting que use el pooler de Supabase (no solo Railway) va a fallar tarde o temprano con este mismo error, y puede pasar desapercibido un rato porque las primeras requests después de un deploy nuevo a veces funcionan (antes de que el pool reutilice conexiones).
  **CORS agregado**: `SecurityConfig` ahora tiene un `CorsConfigurationSource` (antes no hacía falta, todo era same-origin en local). Orígenes permitidos vía `app.cors.allowed-origins` (env var `APP_CORS_ALLOWED_ORIGINS`, default `https://www.mygym.cl,https://mygym.cl,http://localhost:4300`) — agregar cualquier dominio nuevo (previews de Vercel, etc.) ahí si hace falta.
  **Bug real encontrado por el build limpio de Railway, no por los tests locales:** `ReservationService.listOccurrences` capturaba la variable de control de un `for` clásico (`date`, reasignada en el propio for) dentro de un lambda — "local variables referenced from a lambda expression must be final or effectively final". Esto es un error de compilación real (JLS), pero **Maven local nunca lo detectó** porque nunca se corrió `mvn clean` en toda la sesión — la compilación incremental reusaba el `.class` ya compilado de ese archivo (que no se había vuelto a tocar) y nunca lo recompilaba. Lección: correr `mvn clean compile`/`clean test` al menos una vez antes de confiar en que "ya compiló antes" sigue siendo válido, sobre todo antes de un deploy real.

- (2026-09-13) **Auditoría de contraste de color (pedido explícito de UX) — bug sistémico real en `ion-card`/`ion-card-title`, no solo en Planes.** El usuario reportó que el título de las tarjetas de Planes era casi invisible; verificado visualmente con chrome-devtools MCP (debug route + `ng.getComponent()`) que era el MISMO bug en "Bloques / horarios" y en cualquier `ion-card-title`/texto plano dentro de `ion-card-content` de toda la app. Causa raíz: `ion-card` (y `ion-card-title`, que tiene su propio color por defecto hardcodeado, no heredado) **no leen `--ion-text-color`/`--brand-text` como sí lo hacen `ion-item`/`ion-label`** — sin un `--color` explícito, el texto cae al gris casi negro por defecto de Ionic (`rgb(38,38,38)` para `ion-card-title`, `rgb(115,115,115)` para texto plano), invisible contra los fondos oscuros de la app. **Fix global en `styles.scss`**: `ion-card { --color: var(--brand-text); }`, `ion-card-title { color: var(--brand-text); }`, `ion-card-content { color: var(--brand-text); }`, `ion-card-subtitle { color: var(--brand-text-dim); }`. Esto arregla TODAS las páginas que usan `ion-card` (gym-admin, gym-list, gym-form, home), no solo Planes.
  **Segundo hallazgo del mismo audit**: el `<p>` secundario dentro de `ion-label` (ej. "Cupo: 15", el email debajo del nombre de un socio) también usa un gris hardcodeado de Ionic con contraste medido **~2.1:1 contra el fondo de `ion-item`** (falla WCAG AA, que exige 4.5:1) — fix: `ion-label p { color: var(--brand-text-dim) !important; }` (contraste resultante ~6.4:1). El `!important` fue necesario porque el estilo de Ionic pesa más por orden de carga, no por especificidad.
  **Tercer hallazgo**: en `/member` y `/j/:slug` (join), `ion-content` **no re-declaraba `--ion-color-primary`/`--ion-color-primary-contrast`** aunque `ion-header` sí — como son elementos HERMANOS (no ancestro-descendiente), las custom properties de uno no llegan al otro. Consecuencia real en `/member`: los botones "Elegir plan" quedaban siempre en el lima por defecto en vez del color real del gimnasio (verificado con tema azul `#3da5ff` — el botón salía verde). Fix: agregar las 4 variables de tema (`--ion-color-primary(-contrast)`, `--brand-accent(-contrast)`) también al binding de `ion-content` en ambos archivos, replicando exactamente el patrón que `gym-admin.html` ya usaba correctamente en ambos elementos. **Patrón a recordar para cualquier página nueva con theming dinámico: bindear las mismas custom properties en CADA elemento de nivel superior que las necesite (header Y content por separado), nunca asumir que se heredan entre hermanos.**
  **Técnica usada para todo el audit**: ruta temporal `_debug-gym-admin`/`_debug-member` en `web.routes.ts` (sin guard) + `ng.getComponent()` para inyectar gym/plans/blocks/membership mock con distintos `themeColor` (lima, azul, ámbar) — permite verificar visualmente con chrome-devtools MCP sin necesitar login real ni forjar JWT. Rutas debug removidas antes de cerrar (verificado `grep -c "_debug"` → 0).
- (2026-09-13) **Identidad en el navbar de gym-admin + banner de bienvenida sutil** (pedido explícito). Intento inicial de meter "admin · Sección" como segunda línea DENTRO de `<ion-title>` con `display:flex;flex-direction:column` en el host **no funcionó**: `ion-title` tiene shadow DOM (`<div class="toolbar-title"><slot></slot></div>`) y el `display:flex` en el host no se propaga al wrapper interno que controla el layout del contenido proyectado — las dos líneas se veían pegadas en una sola. **Fix real**: un `<div class="admin-identity-bar">` plano, HERMANO de `<ion-toolbar>` (no hijo de `ion-title`), evita pelear con el shadow DOM de Ionic. **Lección general: para forzar un layout de dos líneas dentro de un componente Ionic con shadow DOM (ion-title, ion-card-title, etc.), usar un elemento plano hermano en vez de anidar dentro del componente** — el mismo tipo de gotcha que ya se documentó para `--background` en `ion-content` (hay que usar la custom property que el componente expone, no CSS directo sobre su estructura interna). Banner de bienvenida (`.admin-welcome`, tono de negocio, sin foto — deliberadamente más sutil que el hero de `/member`) con saludo + un tip rotativo de `ADMIN_TIPS` (mismo patrón que `MOTIVATIONAL_QUOTES` de member.ts, elegido una vez por carga con `Math.random()`).

## Aprendizajes / gotchas

- (2026-09-03) **`proxy.conf.json` con glob `/algo/*` solo matchea UN segmento de path.** `/api/*` proxea `/api/gyms` pero NO `/api/gyms/2` ni `/api/gyms/2/blocks` (caen al fallback SPA de `ng serve`, devolviendo `index.html` con status 200 y `Content-Type: text/html` — un 200 "fantasma" que no es fácil de notar sin mirar el `Content-Type`). Usar `/api/**` para que matchee cualquier profundidad de subrutas. Además, `ng serve` solo lee `proxy.conf.json` al arrancar — hay que reiniciarlo después de editarlo, `ng serve` no hace watch de ese archivo.
- (2026-09-03) **Ionic fija `body`/`ion-app` en `position: fixed; height: 100%` (shell de app nativa) — el documento NUNCA scrollea.** Una página nueva con HTML plano (sin `<ion-content>`) se ve recortada al alto del viewport y no hace scroll aunque tenga contenido debajo: `window.scrollTo`, `document.body.scrollHeight` y un `IntersectionObserver` con `root: null` no fallan con error, simplemente no pasa nada porque el contenedor real no se mueve. Toda página nueva (landing incluida) debe envolver su contenido en `<ion-content>` para heredar el scroll interno de Ionic.
- (2026-09-03) **Consecuencia del punto anterior:** el screenshot `fullPage` de chrome-devtools MCP mide `document.documentElement.scrollHeight` para decidir el alto a capturar — como ese scrollHeight queda fijo al viewport dentro de `ion-app`, un `fullPage` en cualquier página de este proyecto solo trae el hero/primer viewport, aunque haya mucho más contenido debajo. Para verificar una página completa hay que scrollear el `ion-content` real (`await content.getScrollElement()`) por tramos y sacar screenshots normales, no confiar en `fullPage`.
- (2026-09-04) **`@DataJpaTest` sin `@AutoConfigureTestDatabase(replace = Replace.NONE)` falla desde que se sacó H2 del classpath** ("Failed to replace DataSource with an embedded database for tests") — Spring Boot por defecto intenta reemplazar el datasource de un `@DataJpaTest` por uno embebido, y como el proyecto usa Postgres real siempre (sin H2 de respaldo), no hay con qué reemplazarlo. `GymRepositoryTest` tenía este gap desde el cambio a Supabase (nadie había corrido `mvn test` completo hasta ahora); el fix es agregar esa anotación a cualquier `@DataJpaTest` nuevo.
- (2026-09-03) **Nunca ocultar contenido con `opacity: 0` a la espera de que JS (scroll-reveal, IntersectionObserver) lo haga visible.** Si `prefers-reduced-motion` está activo en el SO/navegador, o el JS falla/tarda, el contenido queda invisible para siempre y no hay error en consola que lo delate — se vive como "la página está vacía/pobre". Patrón correcto: contenido visible por defecto (`opacity: 1`), la animación de scroll solo agrega un `transform` sutil encima, nunca gatea la visibilidad.
- (2026-09-08) **`<ion-modal>` con contenido inline (`<ng-template>` + `<ion-header>`/`<ion-content>` como hijos directos, sin wrapper) colapsa el `ion-content` a una altura mínima (~56px) y le aplica `contain:size` + `overflow:hidden` — todo lo que queda debajo del primer campo del form se recorta invisible, aunque el DOM esté perfectamente hidratado (Angular/Ionic no tiran ningún error, `getBoundingClientRect()` de cada campo devuelve valores correctos, `getComputedStyle` también — el bug no se detecta inspeccionando estilos computados, solo mirando el screenshot real).** Causa: sin la clase `.ion-page` en el elemento raíz del contenido, no se aplica la regla `.ion-page{display:flex;flex-direction:column;height:100%}` de `@ionic/angular/css/core.css` que hace que `ion-content` (flex child) se estire para llenar el modal. Fix: envolver el `<ion-header>`+`<ion-content>` del componente de contenido del modal en `<div class="ion-page">...</div>`. Aplica a cualquier modal Ionic-Angular con contenido inline (no a los creados vía `modalController.create()`, que sí agregan la clase solos).
- (2026-09-08) **`vercel-landing/public/` NO se regenera solo — es un paso manual fácil de olvidar.** `ng build landing` escribe en `dist/landing/browser/`, pero Vercel sirve desde `vercel-landing/public/` (`outputDirectory` en `vercel.json`). Si se corre `vercel --prod` sin antes copiar `dist/landing/browser/*` → `vercel-landing/public/`, el deploy "funciona" (Vercel da `READY`, el HTML se actualiza con nuevo `last-modified`) pero sirve los chunks JS **viejos** porque `public/` no cambió — un falso positivo silencioso, nada indica el error salvo comparar el contenido real de los chunks servidos contra el fix esperado. Checklist de deploy de la landing: `ng build landing` → `rm -rf vercel-landing/public/* && cp -r dist/landing/browser/* vercel-landing/public/` → `cd vercel-landing && vercel --prod --yes`.
- (2026-09-08) **Bug de seguridad real (no solo de UI): el panel `/gym-admin` (dueño de gimnasio) llamaba a los mismos endpoints `/api/gyms/{id}` que el panel super-admin**, protegidos con `hasRole("SUPER_ADMIN")` desde el cambio del 2026-09-07 — cualquier `GYM_ADMIN` real recibía 403 en todo (ver gym, listar/crear/editar/eliminar bloques), aunque el login funcionara. - (2026-09-08) **chrome-devtools MCP puede quedar en `CONNECT_TIMEOUT` para la sesión aunque `claude mcp list` lo muestre "Connected"** (el problema es de la conexión de esta sesión puntual, no del server) — ni reconectar vía `/mcp` ni un `/compact` lo revivieron en un caso real. Workaround que no depende de la MCP: usar Playwright apuntando a un Chrome/Edge ya instalado en el sistema (`chromium.launch({ channel: 'chrome', headless: true })`), evitando la descarga del binario propio de Playwright (que además puede fallar en redes con WARP — ver `user_windows_network_quirks`). Da control real de navegador (DOM, computed styles, screenshots, network) sin la MCP. Para probar paneles con auth (Google OAuth) sin loguearse de verdad: forjar un JWT HS256 con el mismo `APP_JWT_SECRET` de Railway/local (claims `sub`, `userId`, `role`, `gymId`, `iat`, `exp` — ver `JwtService.java`) e inyectarlo en `sessionStorage` (`mygym.auth`, ver `auth.service.ts`) antes de navegar a una ruta protegida.

- (2026-09-08) **Row Level Security (RLS) estaba deshabilitado en las 4 tablas públicas** (`gym`, `gym_block`, `app_user`, `reservation`) — Supabase avisó por mail que cualquiera con la URL del proyecto podía leer/editar/borrar todo vía su API REST auto-generada (PostgREST), que expone cualquier tabla sin RLS a los roles `anon`/`authenticated`. El backend nunca usa esa API (se conecta directo por JDBC como el rol dueño de las tablas, que **bypassea RLS**), así que el fix (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY` sin policies, en `V4__enable_row_level_security.sql`) cierra la API pública sin afectar la app.
  **Gotcha grave que causó una caída real de producción:** intentar incluir `ALTER TABLE flyway_schema_history ENABLE ROW LEVEL SECURITY` en esa misma migración **cuelga el deploy indefinidamente** — Flyway usa esa tabla para su propio locking/bookkeeping mientras la migración corre, así que alterarla desde adentro de una migración que Flyway está ejecutando genera un deadlock real contra el propio Flyway (confirmado con `pg_stat_activity`: una sesión "idle in transaction" corriendo la query interna de Flyway, bloqueando a la sesión que corre el `ALTER`, que a su vez bloquea a Flyway). Confirmado empíricamente: `getComputedStyle(document.documentElement).getPropertyValue('--ion-background-color')` daba `#121212` (paleta genérica de Ionic) en vez de `#1e2c30` (marca) con `prefers-color-scheme: dark` activo. **Fix:** se sacó el `@import` de `dark.system.css` por completo — mygym tiene un solo tema (oscuro, fijo de marca), nunca un modo claro al que "volver", así que no tiene sentido seguir el dark-mode automático del sistema. Se agregó `color-scheme: dark;` en `:root` para que los controles nativos (scrollbar, form controls) also usen la paleta oscura en vez de adivinar una clara (el usuario reportó el scroll con un color que no respetaba el tema — mismo origen). **Nunca volver a importar esa hoja de paleta automática** mientras el producto siga siendo de un solo tema fijo.

Válido como técnica general: para depurar layout/CSS de un componente autenticado, aislarlo en una ruta pública temporal en vez de forjar credenciales.

## Cómo mantener esta skill

Cada vez que resolvamos algo no trivial, tomemos una decisión de arquitectura, o descubramos una convención o gotcha del proyecto: agregar una entrada corta (qué + por qué) en la sección que corresponda. Fecha las entradas si el contexto puede volverse obsoleto.
